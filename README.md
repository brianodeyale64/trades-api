# Trades API 📈

A REST API for recording and querying stock trades, built with **Django** and **Django REST Framework**.

It lets you create buy and sell trades, list them, filter them by trade type or user, and fetch a single trade by id. Invalid trades are rejected with clear error messages, and any method that isn't supported returns the correct HTTP status code.

I built this to get hands-on with Python backend development. I mainly work in Java (Spring Boot), so this project was about learning how the same ideas (models, validation, controllers and routing) work in Django.

## The Trade Model

Each trade looks like this:

```json
{
  "id": 1,
  "type": "buy",
  "user_id": 23,
  "symbol": "ABX",
  "shares": 30,
  "price": 134,
  "timestamp": 1531522701000
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | Integer | Auto-generated by Django |
| `type` | String | `buy` or `sell` |
| `user_id` | Integer | The user who made the trade |
| `symbol` | String | Stock symbol, e.g. `ABX` |
| `shares` | Integer | Must be between 1 and 100 |
| `price` | Integer | Price per share |
| `timestamp` | Big Integer | Time of the trade in milliseconds |

---

## Endpoints

| Method | URL | What it does | Status |
|---|---|---|---|
| `POST` | `/trades` | Create a new trade | `201 Created` |
| `GET` | `/trades` | List all trades, ordered by id | `200 OK` |
| `GET` | `/trades?type=buy` | Only buy (or sell) trades | `200 OK` |
| `GET` | `/trades?user_id=23` | Only trades by that user | `200 OK` |
| `GET` | `/trades/<id>` | Get one trade | `200 OK` / `404 Not Found` |
| `PUT` / `PATCH` / `DELETE` | `/trades/<id>` | Not allowed, trades can't be changed | `405 Method Not Allowed` |

Filters can be combined, e.g. `/trades?type=sell&user_id=50`.

---

## Validation

Before a trade is saved, the API checks:

- `shares` is between **1 and 100**
- `type` is either **`buy`** or **`sell`**

If either check fails, the API returns **`400 Bad Request`** with a message for each problem:

```json
{
  "type": ["Type must be 'buy' or 'sell'."],
  "shares": ["Shares must be between 1 and 100."]
}
```

## Example Requests

Create a trade:
```bash
curl -X POST http://127.0.0.1:8000/trades \
  -H 'Content-Type: application/json' \
  -d '{"type": "buy", "user_id": 23, "symbol": "ABX", "shares": 30, "price": 134, "timestamp": 1531522701000}'
```

Get all buy trades:
```bash
curl 'http://127.0.0.1:8000/trades?type=buy'
```

Try a blocked method (returns 405):
```bash
curl -i -X DELETE http://127.0.0.1:8000/trades/1
```

## How It Works

The project follows Django's standard structure, with each file doing one job:

| File | Job | Spring Boot equivalent |
|---|---|---|
| `app/models.py` | Defines the Trade table | `@Entity` class |
| `app/serializers.py` | Converts between JSON and Trade objects, and validates input | DTO + `@Valid` |
| `app/views.py` | Handles requests, filtering and allowed methods | `@RestController` |
| `project/urls.py` | Maps `/trades` URLs to the view | `@RequestMapping` |

**Request flow:**
```
Request → urls.py → views.py → serializers.py (validate) → models.py (database) → JSON response
```

### Key design decisions
- **`ModelViewSet`** handles the standard list, retrieve and create logic, so I didn't have to write each endpoint by hand.
- **`http_method_names = ["get", "post"]`** restricts the API to reading and creating. Trades are treated as permanent records, so update and delete return `405`.
- **`get_queryset()`** applies the `type` and `user_id` filters from the URL query string, and always orders results by id.
- **`validate_shares` / `validate_type`** in the serializer keep validation in one place, separate from the view logic.
- **`BigIntegerField`** for `timestamp`, because millisecond timestamps are too big for a normal integer.

## Bugs I Hit (and Fixed)

- **App not registered:** the Trade table wasn't being created because the app wasn't properly listed in `INSTALLED_APPS`. Adding it and re-running migrations fixed it.
- **500 error on DELETE:** sending `DELETE /trades/1` crashed the server instead of returning 405. Django's `APPEND_SLASH` setting tried to redirect the request to `/trades/1/`, which it can't do for a DELETE. I fixed it by setting the router to `trailing_slash=False`, so the URLs match the spec exactly. It also taught me that library versions matter: a trailing-slash trick that worked in an older version of DRF didn't work in mine.

## Running Locally

```bash
git clone https://github.com/brianodeyale64/trades-api.git
cd trades-api
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt
python manage.py migrate
python manage.py runserver
```

Then open **http://127.0.0.1:8000/trades** in your browser to use Django REST Framework's built-in interface.
